# Appendix D – Dual‑Key Apollo‑2 Kill Switch and HSM Aegis‑2

## HSM Aegis‑2 Hardware Security Module

### Physical Specifications

- **Form factor:** Custom ASIC (production) / Raspberry Pi Pico RP2040 (emulation for training)
- **Package:** Tamper‑resistant epoxy potting, active mesh shielding
- **Power:** Separate battery backup for intrusion detection (cannot be disabled by main system)

### Cryptographic Core

- **Dual signature algorithms:**
  - Ed25519 (classical, high‑speed)
  - CRYSTALS‑Dilithium (post‑quantum, NIST standard)
- **Key storage:** One‑time programmable (OTP) memory, zeroed upon tamper
- **Signature generation:** Fixed number of clock cycles (e.g., 12 000 000 cycles @ 1.2 GHz)
  - **Cycle count tolerance:** ±1 cycle
  - **Absolute time tolerance:** ±5 μs (due to temperature/voltage effects, but cycle count must match exactly)
  - **Rationale:** Removes unrealistic nanosecond jitter requirements while still detecting clock glitches

### Analog Intrusion Detector (ADI)

| Detector | Measurement | Trip Condition |
|----------|-------------|----------------|
| Thermal sensor | Die temperature | Change >2 °C per signature window |
| Voltage monitor | Core voltage | Deviation >5% from nominal |
| Clock monitor | PLL lock, frequency | Cycle count mismatch |
| Laser sensor | Photodiodes on die surface | Any illumination >1 μW |
| Glitch detector | Power line transient | Rise time <100 ns, amplitude >10% |

**If any detector trips:** HSM erases keys, stops responding, and signals Apollo‑2 to cut power.

### Lifecycle Limits

- **Maximum signatures:** 1 000 000 per HSM
- **Rate limit:** Hardware enforced (minimum 10 ms between signatures)
- **After limit reached:** HSM permanently locks, requires physical replacement

## Apollo‑2 Dual‑Key Kill Switch

### Physical Architecture

```
[IBSA Global Key (validator consensus 2/3)]  ──┐
                                                │
                                                ├──► [AND gate] ──► MOSFET power cutoff
                                                │
[Sovereign Key (State HSM)]                ──┘
```

### Activation Requirements

**Both** conditions must be true for power cutoff:

1. **Global key** – Generated by IBSA upon:
   - Validator consensus of 2/3 of all States Parties
   - Confirmed violation of Aegis‑1 Treaty (e.g., confirmed obedience simulation, uncertified AI operation)
   - UN Security Council resolution (for extreme cases)

2. **Sovereign key** – Supplied by the State where the chip is physically located:
   - Generated by the State’s national HSM
   - State may refuse to sign; consequence: automatic loss of validator status and sanctions under Article 3.4
   - No external entity can force the signature; but refusal isolates the State

### Kill Switch Operation Timeline

1. **Detection:** Local HSM detects violation or receives global alert.
2. **Consensus (if global):** 2/3 of validators sign violation confirmation (24‑72 hours for non‑emergency, 1 hour for “Red Dawn”).
3. **Global key broadcast:** IBSA transmits signed activation vector via encrypted satellite channel.
4. **Sovereign key injection:** State’s HSM receives request, authorised official approves (manual or automated by policy).
5. **AND gate:** Both keys present → MOSFET opens → physical power cut to AI accelerators.
6. **Fallback:** If State refuses to provide sovereign key within defined timeout (e.g., 24 hours for emergency), the State automatically loses validator status and faces sanctions. The AI continues to run, but only on that State’s isolated network (disconnected from global infrastructure).

### Anti‑Tamper Measures

- **Attempt to short MOSFET:** Secondary fuse blows, permanent cut.
- **Attempt to replace Apollo chip:** Unique serial number chaining; replacement breaks HSM signature chain.
- **Attempt to disable AND gate logic:** Mesh detects open circuit → zeroisation.

### Emulation for Training (RP2040)

The `hsm_emulator` directory contains a C++ firmware that emulates:
- Fixed cycle count timing (using `timer_hw->timerawl`)
- Temperature delta detection (via internal ADC reading)
- Dual‑key logic (simulated with test keys)

**Limitations of emulator:**
- No physical anti‑tamper mesh
- No real cryptographic acceleration (simulated hash)
- Jitter tolerance relaxed to microseconds for test environment

**For production:** Custom ASIC required, fabricated at certified foundry with IBSA oversight.
